# Rate limits and abuse controls plan

**Scope:** P0-B2a now implements the first staging-safe backend slice described by this plan. It does not add a shared store, external provider, migration, or production-complete distributed enforcement.

**Current position:** Slotzy is staging-ready for solo-founder QA and **not production-ready**. The limits below are initial safety bounds to validate and tune; they are not production approval, an SLA, or evidence of external-tester validation.

## Current exposed surface

The current Express surface includes public authentication, booking-context, booking creation, opaque manage-token lookup/cancellation, manage-link recovery, authenticated account and shop operations, restricted administration/development routes, and health. There is no backend endpoint for the static operator-assisted account-recovery help text, and no self-service password-reset endpoint. `/api/public/manage/recover` is booking manage-link recovery, not staff-account recovery. P0-B2a replaces the route's earlier isolated guard with the common bounded in-process limiter described below.

## P0-B2a implementation status

The reusable bounded in-process limiter, privacy-safe HMAC keys, generic `429` responses, bounded `Retry-After`, and allowlisted `abuse.rate_limited` events are implemented for login, anonymous booking creation, public manage lookup, public cancellation, and manage-link recovery. Focused tests cover legitimate requests, limit boundaries, expiry and cleanup, bounded counter storage, route isolation, response non-enumeration, and event redaction.

This package is ready for a Render staging deploy and guarded validation; that deployment is not recorded as complete here. Source keys currently derive from the direct socket address and intentionally do not trust forwarded headers until Render proxy behavior is explicitly validated. Counters remain instance-local and reset on deploy, so P0-B2a reduces staging risk but is not a production control. No monitoring provider or external rate-limit store was added.

## Key and failure-mode rules

- A **coarse source** means a privacy-approved, short-retention HMAC or coarse network bucket derived at request time. Never emit or persist a raw IP address unless a separate privacy decision explicitly approves it.
- An **account key** is a one-way keyed digest of a normalized login identifier or, after authentication, the stable internal account ID. Do not log the digest or raw identifier; event output needs only `key_type=account` if that field is approved.
- A **shop key** is an opaque internal shop ID usable by the limiter. Events should use an approved redacted shop reference, not public/private profile data.
- A **manage key** may use the server-derived manage-token hash/HMAC inside the limiter. Never log it, return it, use it as an event label, or let different limits reveal whether the token is valid.
- Every key includes the safe route name and environment. Limits on one endpoint must not unexpectedly consume another endpoint's budget.
- Prefer a working local fallback when a shared limiter is unavailable. “Fail closed” below means return a generic temporary-unavailable or rate-limited response when neither the shared limiter nor an approved bounded fallback is available. “Fail open” means allow the authorized application request and emit a safe limiter-degraded event.

### Category-specific log exclusions

- **Auth login:** never log username/email input, password, password hash, JWT, `jti`, authorization header, raw IP, or raw body.
- **Registration:** never log proposed username/contact fields, password/hash, raw body, raw IP, or duplicate-account detail in limiter events.
- **Password change:** never log current/new passwords, password hashes, JWT/`jti`, account input, authorization header, or raw body.
- **Operator-assisted account recovery help/info:** never log recovery text input, account/contact value, reset token, support-channel private link, or account-existence result.
- **Public booking creation:** never log customer name/contact, appointment payload, manage token/hash, private receipt link, raw body, or raw IP.
- **Booking availability/public lookups:** never log query strings, full URLs, customer inputs, raw IP, or non-public shop/provider data.
- **Public manage-token lookup:** never log manage token/hash, private link, booking/customer data, headers carrying the token, full URL, query, or fragment.
- **Customer manage actions:** never log manage token/hash, private link, booking/customer data, cancellation form text, token header, or raw body.
- **Booking manage-link recovery:** never log contact value/digest, recovered token/link, recipient, notification content, raw body, or whether a match existed.
- **Staff booking mutations:** never log booking/customer payloads, contacts, private notes, JWT/`jti`, authorization header, or raw body.
- **Shop/service/profile and staff reads:** never log response bodies, private profiles, contacts, full query/URL values, JWTs, or authorization headers.
- **Authenticated shop/service/availability mutations:** never log branding data, profile/contact fields, availability notes, JWTs, authorization headers, or raw bodies.
- **Health/readiness:** never log request headers, proxy chains/raw IPs, secrets, dependency credentials, or full probe URLs.
- **Static frontend/PWA assets:** never log URL queries/fragments, referrers containing private links, raw IP without privacy approval, or browser storage.
- **Restricted admin/development/notification routes:** never log admin secrets/tokens, exports, customer data, email bodies/recipients, notification payloads, or destructive request bodies.

## Safe response and observability contract

All rejected requests should use HTTP `429` with a stable, route-appropriate generic code and a bounded `Retry-After` value. The response must not state the counter, key, account existence, manage-token validity, contact match, booking existence, or internal provider decision. Equivalent invalid and limited manage/recovery requests must remain indistinguishable enough to avoid an enumeration oracle.

Emit an allowlisted `abuse.rate_limited` event containing only: environment, service, safe route name, method, status, category, generic outcome/error code, correlation ID, release, and an approved key-type label such as `coarse_source`, `account`, `shop`, or `manage`. A separate `abuse.limiter_degraded` event should identify safe route/category and fallback outcome when a limiter store fails.

Never log passwords, password hashes, JWTs, `jti` values, authorization headers, reset tokens, manage tokens, manage-token hashes, private links, service-role keys, raw IP addresses, raw request bodies, customer contacts, full email/phone values, user-entered fields, full URLs, query strings, or fragments. Do not encode these values into metric labels, fingerprints, correlation IDs, screenshots, or test artifacts.

## Implementation phases

1. **Phase 1 — in-process staging-safe route limits:** add a small bounded-memory limiter with expiry/cleanup, privacy-safe composite keys, generic responses, and explicit per-route policies. Treat it as staging-only because counters reset on deploy, are not shared across Render instances, and can be bypassed by traffic distribution.
2. **Phase 2 — production shared-store decision:** select a durable/shared limiter appropriate to Render topology, define availability/fallback behavior and retention, complete a privacy review of network-derived keys, and document operational ownership. A database migration is not assumed; a provider-native or dedicated ephemeral store may be preferable to application tables.
3. **Phase 3 — focused tests and observability integration:** cover allow/deny boundaries, window expiry, generic account/manage/recovery responses, key isolation, store failure modes, and `abuse.rate_limited`/`abuse.limiter_degraded` redaction.
4. **Phase 4 — alert thresholds and tuning:** begin with counts/daily review in staging, establish wider-beta baselines, alert on sustained auth/manage/booking limits or service-impacting attack patterns, and prevent high-cardinality labels.
5. **Phase 5 — production/privacy review:** approve source-key derivation and retention, shared-store access, thresholds, fail modes, incident response, support copy, and false-positive recovery before production.

## Recommended first implementation package

**P0-B2a is implemented locally and awaits Render staging deployment/validation.** It covers login, anonymous booking creation, and public manage actions (`GET /api/public/manage`, `PATCH /api/public/manage/cancel`, and `POST /api/public/manage/recover`) with the common limiter and safety contract. Registration can reuse the helper afterward; password change and authenticated staff routes should follow only after the staging thresholds and source derivation are validated.

This is the smallest package covering the highest-risk combination: credential attacks, unauthenticated write spam, private manage-link probing, cancellation abuse, and recovery-message amplification. In-memory limits are acceptable for controlled single-instance staging because they reduce immediate abuse risk without new infrastructure. They are not production-complete: deploys reset counters, multiple instances do not share state, memory pressure requires bounds/cleanup, and a determined attacker can distribute requests. Production requires the Phase 2 shared-store/privacy decision and tested fallback behavior.

## Highest-risk category

Public manage-token and manage-link recovery routes carry the highest confidentiality risk because weak controls can become token-validity, appointment-existence, or contact-existence oracles. Public booking creation carries the highest availability/cost risk because it can create durable spam records and amplify notifications. Both belong in the first implementation package alongside login.

## Platform implications

- **Netlify:** not required for the first backend package. Static/PWA volumetric controls remain a later provider-native decision if measured abuse warrants them.
- **Render:** required to deploy and validate backend limits, confirm proxy/source-key handling, and observe safe limiter events. Production topology affects the shared-store decision.
- **Supabase:** no migration is required for the plan or the recommended in-process staging package. Do not use application tables for production rate limiting without a separately reviewed design.
